# Sponari — working notes

Sponari is a Chromium fork maintained as a patch set. This repo is the whole
product: patches, branding assets, and the tooling that pins, rebases and
rebuilds on top of each Chromium stable. The Chromium checkout lives outside
the repo (`.chromium_dir` file or `SPONARI_CHROMIUM_DIR`, default
`../chromium/src`) and is never committed anywhere.

## Hard rules

- Don't start long jobs (`scripts/sync.py`, `gclient`, `fetch`, `autoninja`,
  `gn gen` on the real checkout). Print the command; the user runs it.
- The user agent must keep looking like Chrome. Don't touch UA code
  (`components/embedder_support/user_agent_utils.cc`) or UA-CH brands.
- Never rename `.grd` message IDs. Change string values only.
- `is_chrome_branded` stays false.
- Files in `patches/` are generated by `export_patches.py`, never edited by
  hand.
- Scripts run on `/usr/bin/python3` (3.9), stdlib only. No pip, no `match`.

## How the patch model works

`src` HEAD always sits exactly on the tag in `.chromium_version`. Patches are
applied to the working tree and never committed inside `src`, so
`git -C <src> diff` is always the complete Sponari delta.

One patch per upstream file. The filename is the upstream path with `/`
replaced by `-`, but the real target is parsed from the diff header.

Making a change:

    vim <src>/chrome/app/chromium_strings.grd    # edit the upstream file
    python3 scripts/export_patches.py            # regenerate patches/

    # round-trip before committing:
    python3 scripts/reset_patches.py
    python3 scripts/apply_patches.py
    python3 scripts/export_patches.py            # must be byte-identical

    git add patches/ && git commit

Patches are only for files that already exist upstream. Renames aren't
supported — express them as delete + add.

Whole **new** files live in `overlay/`, which mirrors the `src/` layout and is
copied in by `apply_patches.py` (declared in `copy_manifest.json`'s `trees`).
They stay untracked inside `src`, so `git -C <src> diff` is still exactly the
patch set. Edit under `overlay/`, never in `src` — apply refuses to clobber a
hand-edited copy. Inner loop:

    vim overlay/chrome/browser/ui/webui/sponari_settings/…
    python3 scripts/apply_patches.py --copies-only

Binaries that *replace* an upstream asset go through `resources/branding/` +
`copy_manifest.json`'s `copies`, never patches. Details in `docs/PATCHES.md`.

## Writing code

In patches: match the style of the file you're editing (Chromium C++ style,
their `.grd` conventions). Keep hunks minimal — every extra changed line is a
future merge conflict. No reformatting, no drive-by fixes.

In scripts: plain readable Python, small functions, output via
`common.info/warn/die`. Try changes against a fixture git repo before the
real checkout (make a tiny repo, tag it with the pinned version, point
`SPONARI_CHROMIUM_DIR` at it).

When designing a feature, prefer the highest layer that can host it. WebUI
(TypeScript/HTML, the `chrome://` pages) rebuilds in seconds,
`chrome/browser` C++ in minutes, widely-included headers under `base/` or
`content/` in hours.

## Upgrades (every ~4 weeks)

`check_upstream.py` notices a new stable, `upgrade.py --prepare` bumps the
pin, the user runs `sync.py`, `upgrade.py --apply` reports conflicts, and
`resolve_conflicts.py` drives `claude -p` over the failures. Nothing is ever
auto-committed: read the report, read the diff, build, then land a single
"Upgrade to X" commit. Full runbook in `docs/UPGRADE.md`.
